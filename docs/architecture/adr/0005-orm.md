# ADR-0005 — Drizzle ORM, not Prisma

**Status:** Accepted
**Date:** 2026-08-24
**Deciders:** Architecture, Phase 1A

## Context

The brief suggests Prisma. Tenant isolation depends on setting a
transaction-local PostgreSQL session variable before every query
([ADR-0003](0003-tenancy-model.md)); the schema needs table partitioning later
([§10.7](../phase-1a/10-database-architecture.md)); and the whole stack shares
one modest VPS with PostgreSQL and a Chromium renderer.

## Options

### A. Prisma
Best-known ORM in the local hiring market, excellent DX, strong migration
tooling. Three concrete problems here, set out in
[§5.2](../phase-1a/05-technology-review.md): RLS session variables require
interactive transactions plus a client extension and fight its connection
handling; the schema language cannot express `PARTITION BY`, so partitioned
tables drift outside the schema; and the Rust query engine adds avoidable
resident memory on a shared host.

### B. Drizzle
Thin TypeScript over SQL. `db.transaction()` plus `set_config(..., true)` is the
natural shape for RLS. Migrations are SQL, so partitioning, partial unique
indexes and policies are ordinary DDL. No engine process. Smaller hiring pool.

### C. Kysely, or raw SQL with a query builder
Maximum control, least schema tooling. More hand-written plumbing than a
two-person team should own.

## Decision

**B — Drizzle**, with SQL migrations checked into the repository.

The deciding reason is the first problem, not the other two: the tenancy
guarantee is the property this system least wants to be clever about. With
Drizzle, "every query runs inside a transaction that first sets the tenant" is
five lines that read like what they do. With Prisma it is a client extension
working against the grain of the library.

## Consequences

**Makes easy:** RLS, partitioning, partial and expression indexes, policies,
`FOR UPDATE` on the receipt sequence, and the SQL-shaped tabulation and
aggregation queries this domain is full of. Lower memory on a shared host.

**Makes hard:** onboarding a developer who knows Prisma — mitigated by Drizzle
being close enough to SQL that the ramp is days, and by the fact that Prisma's
abstractions would have to be learned *and then* worked around. Less
introspection tooling; no Prisma Studio equivalent of the same polish.

**Forecloses:** Prisma-ecosystem tooling. Nothing else — the repository pattern
in `modules/*/infrastructure` means the data-access layer is swappable per
module if it ever needed to be.

## Revisit when

- The team grows past ~4 developers and onboarding speed starts to dominate
  delivery, **or**
- Prisma ships first-class RLS session-variable support and partitioning in its
  schema language, **or**
- Drizzle's release cadence or maintenance status materially degrades.
